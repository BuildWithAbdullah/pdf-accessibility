# Catalogue

Generated by `tools/build-catalogue.mjs` from `lib/catalogue.mjs`. Do not edit by hand:
CI regenerates it and fails if the result differs from this file.

One entry per reason a check can fire, not one per check. Each entry says what the
defect is, what it costs a reader, what the fix is, and what the finding cannot
establish. Entries marked **source** cannot be repaired in the PDF at all.

50 findings across 14 rules.

## tagging

The document has to say it is tagged, and then be tagged.

### `tagging.markinfo.absent`

**No /MarkInfo, so the document does not claim to be tagged**

Assistive technology decides between the structure tree and the raw content stream on this one entry. Without it, every reader falls back to painting order whatever else the file contains.

*Fix.* Add /MarkInfo << /Marked true >> to the catalog, and only once the structure tree below it is real.

*What this finding cannot establish.* This says nothing about whether the structure that follows is correct. A file can carry /Marked true and a complete tree that describes the wrong document.

### `tagging.marked.false`

**/MarkInfo is present and /Marked is false**

This is the explicit statement that the content is not tagged. Some tools write it when a tagging pass was started and abandoned, which leaves a structure tree in the file that nothing will read.

*Fix.* Set /Marked true once the structure tree is complete, or remove the half built tree so the file is honest about what it is.

*What this finding cannot establish.* A false /Marked with no structure tree is a correct statement about an untagged file, not a defect in itself. This finding is about the claim disagreeing with the contents.

### `tagging.structtree.absent`

**/Marked is true and there is no /StructTreeRoot**

The file claims to be tagged and carries no tags. A checker reading only the catalog reports it as tagged, which is how an untagged file acquires a clean report.

*Fix.* Either build the structure tree or set /Marked false. The claim and the contents have to agree.

*What this finding cannot establish.* Detecting this needs the catalog only, so it is cheap and it is also the shallowest thing in this repository. It does not look at a single page.

### `tagging.structtree.empty`

**/StructTreeRoot exists with no children**

An empty root is the same outcome as no root for a reader, but it passes a presence check. Tools that add the root before walking the content leave this behind when the walk fails.

*Fix.* Populate the tree, or remove the root and set /Marked false.

*What this finding cannot establish.* A root with children can still describe none of the page content. The coverage rules, not this one, are what establish that the tree reaches the content.

## language

The document language has to be declared and has to be a language tag.

### `language.absent`

**No /Lang on the catalog**

A screen reader picks a voice and a pronunciation dictionary from this entry. With nothing to go on it uses the user default, so an English document is read with Spanish phonetics to a Spanish user.

*Fix.* Set /Lang on the catalog to the BCP 47 tag of the document body, and override it on any element in another language.

*What this finding cannot establish.* A document level tag does not make a mixed language document correct. Nothing here checks whether the declared language matches the text, which no automated check can do reliably.

### `language.empty`

**/Lang is present and empty**

An empty string satisfies a presence check and carries no information. It is what a template produces when the authoring tool had no language set.

*Fix.* Replace the empty string with the real tag.

*What this finding cannot establish.* Same as the absent case: this is about the declaration, not about the text it describes.

### `language.malformed`

**/Lang is not shaped like a BCP 47 tag**

Values like "English" or "en_US" are common and are not language tags. A reader that cannot parse the value falls back to the user default, so the effect is the same as declaring nothing while the file looks compliant.

*Fix.* Use a tag such as en, en-US or pt-BR. The separator is a hyphen.

*What this finding cannot establish.* This checks the shape, not the registry. A well shaped tag naming a language that does not exist passes.

## title

The document title has to exist, say something, and be the thing the window shows.

### `title.absent`

**No /Title in the document information dictionary**

The title is the first thing announced when the document opens and the label a user picks this window out of twenty by. Without it they get the filename.

*Fix.* Set /Title in the information dictionary to the title a reader would call the document.

*What this finding cannot establish.* This reads the information dictionary only. A title carried solely in XMP metadata is not read here and will be reported as absent.

### `title.empty`

**/Title is present and empty**

An empty title passes every presence check and behaves exactly like no title at all.

*Fix.* Put the title of the document in it. A document information dictionary with an empty title is worth less than one with no title entry, because it stops anybody looking.

*What this finding cannot establish.* Whitespace only titles are treated as empty here, which is a judgement rather than a reading of the specification.

### `title.filename`

**/Title looks like a filename rather than a title**

Authoring tools default the title to the source filename. A user hearing "final_v3_FOR_REVIEW.docx" learns nothing about what they have opened, and a document set titled this way is unnavigable.

*Fix.* Replace it with prose. The test is whether you would read it aloud to somebody.

*What this finding cannot establish.* This is a heuristic on the shape of the string, so a document genuinely called by a filename is a false positive, and a bad title that happens not to look like a filename passes.

### `title.not.displayed`

**A real /Title is present and /DisplayDocTitle is not true**

Without this entry the viewer shows the filename in the window title and the task bar regardless of what the title says. The title is set, and nobody sees it.

*Fix.* Add /ViewerPreferences << /DisplayDocTitle true >> to the catalog.

*What this finding cannot establish.* This is a request to the viewer, not a guarantee. A viewer is free to ignore it, and some embedded viewers do.

## rolemap

A non standard structure type has to map to one a reader understands.

### `rolemap.entry.absent`

**A structure element uses a type that is neither standard nor in the /RoleMap**

A reader meeting an unknown type has no idea whether it is a heading, a paragraph or a table cell. Most treat it as a grouping element with no semantics, so the content is read with none of the meaning the author thought they had added.

*Fix.* Add the type to /RoleMap on the structure tree root, pointing at the standard type that behaves the same way.

*What this finding cannot establish.* Mapping a type makes it readable, not correct. A /RoleMap sending a heading to /P removes the heading from the document outline and this finding will not fire on it.

### `rolemap.target.nonstandard`

**A /RoleMap entry points at another non standard type**

The map exists to end at a type a reader knows. One that points at another custom name leaves the reader exactly where it started, and the presence of the entry makes a checker report the type as mapped.

*Fix.* Point the entry at a standard type. Chains are permitted by the specification and are not worth the risk.

*What this finding cannot establish.* This does not follow a chain to see whether it eventually terminates at a standard type, because a reader is not obliged to follow one either.

## coverage

Every mark on the page has to be reachable from the structure tree, or declared as decoration.

### `coverage.untagged.content`

**Content is painted outside any marked content sequence and is not an artifact**

A reader walking the structure tree never encounters this content, and a reader walking the content stream has no idea what it is. It is the one failure mode that a tagged document and an untagged document do not share: in an untagged file everything is read, here it is silently dropped.

*Fix.* Wrap it in a BDC with an MCID and claim that MCID from a structure element, or mark it /Artifact if it is decoration.

*What this finding cannot establish.* Dropped content is invisible to a reader, so no screen reader test will find it either. This is one of the few findings here that only a file level check can produce.

### `coverage.marked.without.mcid`

**A marked content sequence carries a tag and no MCID**

Without an MCID there is no handle for a structure element to point at, so the sequence looks tagged and is unreachable. It is the shape a tagging tool leaves when it marks up the content before building the tree.

*Fix.* Give the sequence an MCID in its property dictionary and reference it from the element that owns it.

*What this finding cannot establish.* A sequence with an MCID that nothing claims is a separate finding below, because the fix is different: this one is a content stream edit and that one is a tree edit.

### `coverage.orphan.mcid`

**An MCID is painted that no structure element claims**

The content is marked, numbered and unreferenced, so it is read by nothing. Unlike untagged content it will show up in a content stream dump, which is why it survives review.

*Fix.* Add the MCID to the /K of the element it belongs to, or remove the marking and make it an artifact.

*What this finding cannot establish.* This compares the MCIDs painted on a page against the MCIDs the tree names. It cannot say whether the element that should have claimed it exists at all.

### `coverage.parenttree.absent`

**No /ParentTree on the structure tree root**

The tree points down at content and the /ParentTree is the only way back up. Without it a reader that starts from a point on the page, which is what happens on a click, a find, or a touch, cannot discover what the content is.

*Fix.* Build the /ParentTree as a number tree keyed by each page /StructParents and each annotation /StructParent.

*What this finding cannot establish.* Presence is all that is checked here. Whether every key resolves to the right element is the orphan finding above, from the other direction.

## reading-order

The structure tree order and the painting order are two orders, and both are read.

### `order.structure.diverges`

**The structure tree order and the content stream order disagree**

Tagged readers follow the tree. Text extraction, copy and paste, reflow on a small screen, search result context and most untagged fallbacks follow the content stream. When the two disagree one of those populations gets the document in the wrong order, and which population depends on the tool rather than on the file.

*Fix.* Reorder the content stream to match the tree. Reordering the tree instead moves the problem rather than fixing it, because the content stream order is the one the author cannot see.

*What this finding cannot establish.* Agreement between the two orders does not make either order right. Both can be wrong together, which is the normal outcome of a multi column layout exported straight from a page layout tool.

### `order.page.structparents.absent`

**A page paints marked content and has no /StructParents**

The /StructParents number is the key into the /ParentTree for everything on the page. Without it the content is reachable from the tree downward and from nowhere upward, so clicking a word tells a reader nothing.

*Fix.* Give the page a /StructParents whose value is its key in the /ParentTree.

*What this finding cannot establish.* A present /StructParents whose key is missing from the /ParentTree is a different defect and is not separated out here.

## text-layer

There has to be text, and it has to map back to characters.

### `text.layer.absent` **source**

**A page paints an image and no text at all**

This is a scan. There is nothing to read, nothing to search and nothing to select, and no amount of tagging changes that. It is also the single most common reason a PDF cannot be made accessible in the PDF.

*Fix.* Run recognition over the page and check the result by hand, or go back to the source document. Recognition output is a draft, not a fix.

*What this finding cannot establish.* A page of pure illustration with a caption on the facing page is a false positive. More importantly, this finding cannot tell a scan apart from a page whose text is drawn as paths, which is the finding below.

### `text.as.paths` **source**

**A structure element paints paths and no text**

Headings converted to outlines, logos with the company name in them and equations exported as vectors all look like text and extract as nothing. The element is tagged, so a checker sees a correctly tagged heading with no content.

*Fix.* Put the characters back, as real text, or carry them in /ActualText on the element so extraction has something to return.

*What this finding cannot establish.* A genuine diagram tagged as a figure paints paths and no text too, so this fires on correct documents. The element type is what separates them, and this check does not look at how the paths are arranged.

### `text.unicode.unmappable` **source**

**Text is shown in a font with no /ToUnicode and a non standard base font**

The glyphs render and extraction returns the raw character codes, so copy and paste, search and every screen reader produce rubbish. The page looks perfect, which is why this survives visual review.

*Fix.* Embed a /ToUnicode CMap for the font, or use /ActualText on the elements that use it.

*What this finding cannot establish.* The standard 14 fonts are exempt here because a reader can map them from their encoding. A subset font with a /ToUnicode that is itself wrong passes this check.

## artifacts

Page furniture has to be marked as furniture.

### `artifacts.running.tagged`

**The same text is tagged as content on every page**

A running header or a page number tagged as a paragraph is read out between the last sentence of one page and the first of the next, every time. On a forty page document that is forty interruptions, and each one sounds like part of the text.

*Fix.* Mark running headers, footers, page numbers and decorative rules as /Artifact so they stay out of the structure tree.

*What this finding cannot establish.* This needs at least two pages and identical text to fire, so a header that includes the page number in its string will not be caught. Repeated content on a single page is not considered.

## headings

Headings are the document outline, and the outline is how anybody navigates a long PDF.

### `headings.absent`

**A tagged document with no heading element anywhere**

The heading list is the only navigation a screen reader user has in a PDF. There are no landmarks and no skip links. A document with no headings has to be read from the top every time.

*Fix.* Tag the headings that are already visually there. Almost every document has them.

*What this finding cannot establish.* A short document genuinely has none, so this is a prompt rather than a verdict. It also cannot tell a document with no headings from one whose headings are tagged as paragraphs, which is a separate finding below.

### `headings.first.not.top`

**The first heading in the document is not an H1**

A reader jumping to the first heading lands part way down an outline that has no top. In a document set where each file starts at H2 because the H1 lived in a template, the structure reads as a fragment of something else.

*Fix.* Promote the document title to H1, or demote the rest so the outline starts at the top.

*What this finding cannot establish.* This looks at the first heading in tree order. A document that is genuinely one section of a larger work can be correct and will still be reported.

### `headings.level.skipped`

**A heading level is skipped**

H1 followed by H3 tells a reader there is a missing section between them. They cannot tell a skipped level from a section whose heading was not tagged, so they go looking for content that is not there.

*Fix.* Use the next level down, and if the visual size is the reason for the jump, change the styling rather than the level.

*What this finding cannot establish.* Only descent is checked. Returning from H3 to H2 to start a new section is correct and is not reported.

### `headings.empty`

**A heading element with no text**

It appears in the heading list as a blank entry. A user navigating by heading lands on it, hears nothing, and has no way to know whether the problem is the document or their software.

*Fix.* Put the heading text inside the element, or remove the element.

*What this finding cannot establish.* Text held only in /ActualText is treated as text here. A heading whose text is an image with an /Alt is not caught.

### `headings.visual.only`

**Text is painted much larger than the body text and tagged as a paragraph**

This is a heading everywhere except in the structure tree. It is the most common reason a document with visible headings has an empty heading list, and the document looks completely correct on screen.

*Fix.* Change the element type to the heading level the size implies.

*What this finding cannot establish.* This infers intent from font size against the most common size on the page, so a pull quote or a large opening line is a false positive. It cannot see bold, colour or position, which are the other ways a heading is signalled.

## lists

A list that is a list only visually is a list to nobody.

### `lists.visual.only`

**Consecutive paragraphs whose text begins with a bullet or a number**

A real list tells a reader how many items there are and which one they are on. Typed bullets give them a paragraph that starts with a punctuation character, read out as the character, with no count and no position.

*Fix.* Tag the group as /L with an /LI and an /LBody for each item, and move the marker into /Lbl or drop it.

*What this finding cannot establish.* Two consecutive items are enough to fire here, so a paragraph that genuinely opens with a dash followed by another one is a false positive. Numbered steps written as sentences are not caught at all.

## figures

A figure needs a replacement, and the replacement has to be worth hearing.

### `figures.alt.absent`

**A /Figure element with no /Alt**

The image is announced as a figure with nothing after it. A reader cannot tell whether they have missed something important or nothing at all, which is worse than either.

*Fix.* Add /Alt describing what the image conveys in this context, or mark the image /Artifact if it conveys nothing.

*What this finding cannot establish.* Presence of /Alt is checkable and usefulness is not. Everything past this point in this rule is a heuristic.

### `figures.alt.empty`

**A /Figure element with an empty /Alt**

In HTML an empty alt is the correct way to hide a decorative image. In a tagged PDF it is not: the figure is still in the tree and is still announced, now with nothing to say. The equivalent of an empty alt here is /Artifact.

*Fix.* Write a real /Alt, or take the image out of the tree with /Artifact.

*What this finding cannot establish.* This is the one finding in this rule whose fix most often changes the structure rather than the text, which is why it is separated from the absent case.

### `figures.alt.placeholder`

**An /Alt that names the medium rather than the content**

Values like "image", "chart" or "logo.png" are what a tool writes when it is asked to fill the field. They pass every presence check, so a document can be reported fully described while every description is the word "image".

*Fix.* Describe what the image shows and why it is on the page.

*What this finding cannot establish.* This matches a list of known placeholder words and filename extensions, so "Chart" alone is caught and "A chart" is not. A bad description in fluent prose passes.

### `figures.alt.repeats.caption`

**An /Alt that repeats the caption next to it**

The reader hears the same sentence twice, once as the image and once as the caption, and still does not know what the image shows. The caption says what the figure is called; the /Alt has to say what is in it.

*Fix.* Keep the caption and rewrite the /Alt to carry the content, or, when the caption really is the full description, mark the image /Artifact so it is not read twice.

*What this finding cannot establish.* Only an adjacent /Caption element is compared. A caption that is a plain paragraph under the image is not recognised as a caption.

### `figures.alt.verbose`

**An /Alt longer than 250 characters**

There is no way to pause, skip or re-read inside an /Alt. A description that runs to a paragraph is listened to once, at speed, with no way back, which is why long descriptions belong in the page text.

*Fix.* Put a short identification in /Alt and the detail in the document body, where it can be navigated. For a chart that usually means a table of the data.

*What this finding cannot establish.* The threshold is a judgement, not a rule from the specification. A complex diagram may need more, and this will report it.

## tables

A data table needs headers, and the cells need to say which headers are theirs.

### `tables.header.absent`

**A table with no /TH anywhere**

Every cell is read as a value with no label. On a five column table the reader has to count columns from the top of the table for every row, and most cannot, so the table becomes a list of numbers.

*Fix.* Tag the header cells as /TH. If the table has no headers it is a layout table, which is the last finding in this rule.

*What this finding cannot establish.* This counts header cells. It cannot tell whether the cells tagged /TH are the right ones, and a table whose first data row is tagged as the header passes.

### `tables.header.no.scope`

**A /TH with no /Scope in a table that needs one**

With one header row a reader can guess that the headers run down the columns. As soon as there are row headers too, the guess fails, and the cell at the top left of the table is the one that breaks it. The result is values read against the wrong label, which is worse than no label.

*Fix.* Set /Scope to /Column, /Row or /Both on every /TH in a table with headers on two axes.

*What this finding cannot establish.* This fires only where headers appear on more than one axis, because /Scope is optional and harmless to omit on a single header row. Tables whose header arrangement this check reads wrongly will be reported wrongly.

### `tables.headers.dangling`

**A /Headers entry naming an identifier no header cell carries**

An explicit association that points nowhere is worse than no association, because a reader that finds /Headers stops looking for headers by position. The cell ends up with no label at all, on a table that was deliberately marked up.

*Fix.* Correct the identifier, or give the header cell the /ID that is being referenced.

*What this finding cannot establish.* This resolves identifiers inside the document. It does not check that the header a correct identifier reaches is the right header for the cell.

### `tables.header.id.absent`

**A table uses /Headers and some header cells have no /ID**

A table that associates some cells explicitly and leaves others to position is read inconsistently, and which half a reader gets depends on the software. Half an association is the hardest version of this defect to see, because the table demonstrably works in whichever tool the author tried.

*Fix.* Give every /TH an /ID once any cell in the table uses /Headers, and reference them all.

*What this finding cannot establish.* The threshold here is that the table uses /Headers at all. A table with no explicit associations anywhere is judged by the scope finding instead.

### `tables.row.ragged`

**Rows with different cell counts and no span attributes to explain it**

The reader is told the table has one shape and finds another. Navigating by column walks off the end of the short rows, and the cells after the gap are read against the wrong headers for the rest of the table.

*Fix.* Add the /ColSpan or /RowSpan the layout actually uses, or add the empty cells the table is missing.

*What this finding cannot establish.* Only the declared spans are read. A table whose spans are declared and wrong will balance arithmetically here and still be read incorrectly.

### `tables.cell.outside.row`

**A /TH or /TD that is not inside a /TR**

Rows are what make a table two dimensional. Cells hanging directly under the table have a column position and no row, so a reader either flattens the table into a list or gives up on it.

*Fix.* Wrap each run of cells in a /TR.

*What this finding cannot establish.* This checks the immediate parent chain for a /TR. A /TR nested inside an unexpected grouping element is accepted.

### `tables.layout.single.column`

**A table with a single column**

A one column table is a list that has been given a grid to sit in. The reader is told they are entering a table, given the dimensions, and then read a sequence of single cells, all of which is noise around content that was never tabular.

*Fix.* Tag it as /L with list items, or as a sequence of paragraphs.

*What this finding cannot establish.* A genuine single column table of one variable exists and will be reported. The judgement is that the cost of the false positive is lower than the cost of the pattern it catches.

## forms

A form field needs a name a person would recognise, a place in the structure, and a defined tab order.

### `forms.name.absent`

**A widget annotation with no /TU and nothing in the structure to name it**

The field is announced as an edit box with no label. The visible text next to it on the page is not connected to it in any way a reader can follow, so the user is typing into an unnamed box on a form they cannot review.

*Fix.* Set /TU on the field to the visible label text. /TU is what readers announce, and it is the only reliable place to put the name.

*What this finding cannot establish.* A label sitting beside the field is not an association. This check looks for /TU and for /Alt on the field structure element, and treats everything else as absent, which is what readers do.

### `forms.name.empty`

**A widget annotation whose /TU is empty**

Present and empty passes a presence check and announces nothing. It is the normal result of a tool that writes /TU for every field whether or not it found a label.

*Fix.* Fill it in, field by field. There is no way to generate these correctly.

*What this finding cannot establish.* Whitespace only values are treated as empty here.

### `forms.name.is.field.name`

**The /TU repeats the field machine name**

A reader hears "text underscore 7" or "FullName1". The field has a name, it passes every check that looks for one, and it tells the user nothing. This is the most common shape of a form that reports clean and cannot be filled in.

*Fix.* Replace /TU with the label a sighted user reads. Leave /T as the machine name: they are different fields for different audiences.

*What this finding cannot establish.* Comparison is on the normalised strings, so a /TU that merely resembles the machine name passes.

### `forms.field.unstructured`

**A widget annotation with no /StructParent**

The field is not in the reading order. A reader going through the document in order never meets it, and only discovers it by switching to a forms mode, if their software has one. On a page of prose with one field in the middle, the field is invisible.

*Fix.* Add a /Form structure element in the right position in the tree, point it at the annotation with an /OBJR, and set /StructParent on the annotation to match.

*What this finding cannot establish.* Presence of the entry is checked, not whether the element it names sits where the field appears on the page.

### `forms.tabs.absent`

**A page with widget annotations and no /Tabs /S**

Without /Tabs /S the tab order is the order of the annotation array, which is the order the fields were created in. That is often the order they were edited in, so tabbing through a form jumps around the page and no keyboard user can complete it in one pass.

*Fix.* Set /Tabs /S on every page with fields, so tab order follows the structure tree.

*What this finding cannot establish.* This says the order is defined, not that it is right. A /Tabs /S over a structure tree in the wrong order produces a wrong tab order with no finding here, which is why the reading order rules matter to forms too.

### `forms.required.unannounced`

**A required field whose /TU does not say it is required**

The required flag is in the field dictionary and most readers do not announce it. The user finds out on submission, if the form tells them, and on a printed form never. An asterisk in the visible label is not connected to the field.

*Fix.* Say so in /TU, in words, as well as setting the flag.

*What this finding cannot establish.* This looks for the word required or an asterisk in /TU. A form that announces the requirement some other way is reported anyway.

## links

A link needs a description, a place in the reading order, and text worth hearing.

### `links.alt.absent`

**A /Link annotation with no /Contents**

The annotation is the thing a reader activates, and /Contents is its description. Without it some readers announce the destination URL and some announce nothing, so whether the link is usable depends on the software.

*Fix.* Set /Contents on the annotation to the same words as the link text.

*What this finding cannot establish.* A link whose text already reads well is usable in most software without /Contents, so this is a robustness finding rather than a blocker. It is listed separately from the structure finding below because the fix is a different edit.

### `links.unstructured`

**A /Link annotation with no /StructParent**

The link is not in the reading order. The words are read as ordinary text with no indication that they are a link, and the annotation is reachable only by tabbing through annotations, so a reader going through the document in order cannot find it.

*Fix.* Add a /Link structure element containing both the text and an /OBJR for the annotation, and set /StructParent on the annotation.

*What this finding cannot establish.* As with form fields, the entry is checked rather than its position.

### `links.text.is.url`

**The link text is a bare URL**

It is read out character by character, including the protocol and every slash. A long link becomes thirty seconds of punctuation, and a list of them is indistinguishable one from another.

*Fix.* Use the title of the destination as the link text and keep the URL in the action. In print, put the URL in a footnote.

*What this finding cannot establish.* A document that is deliberately printing URLs for a paper reader will be reported. There is no way to tell that intent from the file.
